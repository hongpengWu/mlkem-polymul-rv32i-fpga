# ML-KEM-512 CPU baseline 分析

后续进展（2026-09-25）：快速乘法 CPU 已完成全部 145 条独立阶段测量，
Keccak 占主要 KEM 操作的 71%–81%。实测表和下一步接口任务见
[MLKEM512_PROFILE.md](MLKEM512_PROFILE.md)。下文保留未插桩基线的历史分析，
其中仅由 API 总周期无法回答的问题，现由独立 profiling 提供证据。

本文件的基线结论来自已经完成的三组 PicoRV32 RTL 回归、构建清单、反汇编和 portable C 源码；以下历史数据不包含新增阶段插桩。完整逐条数据见 [summary.md](../results/official_baseline/mlkem512/summary.md)，机器可读数据见 [summary.json](../results/official_baseline/mlkem512/summary.json) 和 [cases.csv](../results/official_baseline/mlkem512/cases.csv)。

## 可以直接确认的结论

三组 CPU 对同一组 ML-KEM-512 官方公开记录各执行 145 条，输入、输出、返回值、地址边界、栈边界和错误输出拒绝检查均通过。计时区间是固件在一次 API 调用前后读取 `rdcycle` 的差值，包含库内清零，不包含 mailbox 传输、启动、testbench 对照和熵源采集。

| 配置 | 算法区间总周期 | 动态 M 指令 | 最大观测栈 | 固件有效字节 |
|---|---:|---:|---:|---:|
| RV32I | 1,400,566,832 | 0 | 12,928 B | 27,808 |
| RV32IM 迭代 | 812,132,449 | 3,486,720 | 12,928 B | 26,272 |
| RV32IM 快速 | 692,273,249 | 3,486,720 | 12,928 B | 26,272 |

145 条记录包含不同操作，不合并成一个“每次 KEM”的平均值；报告和评审应使用按操作分组的均值、P95 和最大值。完整套件的启动总周期没有被拼造，因为结果由关机前 94 条记录和 44 个独立批次合并而成。

| 操作 | 样本数 | RV32I 平均周期 | RV32IM 迭代平均周期 | RV32IM 快速平均周期 | 迭代 / 快速相对 RV32I |
|---|---:|---:|---:|---:|---:|
| KeyGen | 25 | 9,063,344 | 5,887,388 | 5,269,404 | 1.539× / 1.720× |
| Encaps | 50 | 11,798,692 | 6,628,905 | 5,581,097 | 1.780× / 2.114× |
| Decaps（展开私钥） | 20 | 15,740,996 | 8,442,507 | 6,937,739 | 1.864× / 2.269× |
| Decaps（含种子展开） | 10 | 24,731,958 | 14,254,837 | 12,132,085 | 1.735× / 2.039× |
| 公钥检查，返回 0 / -4 | 10 / 10 | 154,004 / 154,015 | 163,748 / 163,759 | 128,932 / 128,943 | 0.940× / 1.194× |
| 私钥检查，返回 0 / -5 | 10 / 10 | 941,441 / 941,452 | 941,441 / 941,452 | 941,441 / 941,452 | 1.000× / 1.000× |

全部 145 条算法窗口的周期合计为 RV32I 1,400,566,832、迭代 812,132,449、快速 692,273,249。快速乘法相对 RV32I 的总算法窗口周期减少约 50.57%；迭代乘法减少约 42.02%。这是纯 CPU baseline 的结果，不能称为 PQC 加速器的端到端加速比。

## 乘法扩展带来的真实收益

两种 RV32IM 使用同一个 `rv32im` 固件镜像和同一 portable C 算法，区别是 PicoRV32 的 `CPU_ENABLE_FAST_MUL`。反汇编和逐条 CSV 给出一个很强的交叉验证：对全部 145 个原始用例，

```text
cycles(iterative) - cycles(fast) = 34 × MUL + 66 × MULHU
```

该等式逐条成立。对应的动态指令计数如下：

| 操作 | MUL / 条记录 | MULHU / 条记录 | 迭代比快速多的周期 |
|---|---:|---:|---:|
| KeyGen | 18,176 | 0 | 617,984 |
| Encaps | 29,824 | 512 | 1,047,808 |
| Decaps | 43,264 | 512 | 1,504,768 |
| 种子 Decaps | 61,440 | 512 | 2,122,752 |
| 公钥检查 | 1,024 | 0 | 34,816 |
| 私钥检查 | 0 | 0 | 0 |

这说明快速乘法带来的差异主要来自 CPU 的乘法执行单元，而不是输入、固件或 testbench 不一致。PicoRV32 中迭代乘法按多个时钟逐步计算；快速乘法使用注册的组合乘积路径。对应实现位于 [picorv32.v](../rtl/cpu/picorv32.v) 的乘法模块，配置映射位于 [run.tcl](../scripts/mlkem512_suite/run.tcl)。

RV32IM 的动态 M 指令全部来自 `MUL` 和少量 `MULHU`；没有观察到 `DIV`、`REM` 或高位有符号乘法。因而当前数据不能支持“除法扩展带来收益”的说法。

## 为什么公钥检查会出现反常结果

合法公钥检查的平均周期是 RV32I 154,004、迭代乘法 163,748、快速乘法 128,932。该结果不是整体基线失效，而是这个短操作的计算组成不同：

- `mlk_kem_check_pk()` 依次执行 `polyvec_frombytes`、`polyvec_reduce`、`polyvec_tobytes` 和常数时间比较，见 `third_party/mlkem-native/mlkem/src/kem.c` 的 `mlk_kem_check_pk`。
- ML-KEM-512 的 `K=2`，`poly_reduce` 处理两个长度为 256 的多项式。RV32IM 反汇编中的每个系数约减使用两个乘法常数；RV32I 则由移位、加法和减法序列实现同一固定常数运算，见 对应反汇编位于本机生成目录 `build/mlkem512_suite/rv32im/disassembly.txt` 和 `build/mlkem512_suite/rv32i/disassembly.txt`，不纳入版本库。
- 因此，迭代乘法的长延迟会在 `poly_reduce` 这个短函数中占主导，反而比 RV32I 的移位加法版本慢；快速乘法消除了这部分惩罚。

私钥检查只计算内置公钥片段的 SHA3-256 并做比较，三组均为 941,441 或 941,452 周期且没有动态 M 指令。这是一个有用的对照：不是所有 PQC 操作都适合通过增加乘法硬件获得收益。

## API 级计时包含哪些阶段

当前计时点包围完整 API，不能从总周期中直接分离出 NTT 或 BaseMul 的准确占比。根据 `kem.c`、`indcpa.c` 和反汇编，可以确认调用路径包含以下工作：

| API | 已知主要阶段 |
|---|---|
| KeyGen | `hash_g`、矩阵生成、噪声采样、秘密向量和误差向量 NTT、mulcache、矩阵向量 BaseMul、Montgomery/约减、打包、`hash_h` 和清零 |
| Encaps | 公钥检查、`hash_h` / `hash_g`、公钥解包、矩阵生成、噪声采样、NTT、矩阵向量 BaseMul、逆 NTT、加法/约减、密文打包和清零 |
| 展开私钥 Decaps | 私钥检查、解密、`hash_g`、重新封装、密文比较、隐式拒绝哈希/条件拷贝和清零 |
| 种子 Decaps | 一次 KeyGen 展开后再执行上述 Decaps 路径；当前 op4 明确把展开时间计入窗口 |

矩阵生成使用 rejection sampling：若初始 SHAKE128 输出未产生足够的合法系数，就继续 squeeze，因此迭代次数可能随输入变化。噪声采样使用固定长度的 SHAKE256 输出和固定循环次数的 CBD，不包含这种可变长度的拒绝采样。KeyGen 的最大/最小差异约 7.4%（RV32I），Encaps 约 5.8%，而普通 Decaps 约 0.6%。这与矩阵采样/XOF 工作量可能变化相符，但历史基线没有采样 squeeze 计数器，不能仅凭当前日志断言某一个高值一定由某一次额外 SHAKE 块造成。

## 对系统设计的含义

1. **阶段实测显示 Keccak 是主要瓶颈。** 在快速乘法配置中，KeyGen、Encaps、展开私钥 Decaps 的 Keccak 独占占比分别为 80.69%、72.96%、71.36%，多项式算术合计为 13.08%、19.13%、21.38%。这使得后续必须同时评估多项式与 Keccak，而不能只看 NTT/BaseMul。
2. **不能只报告乘法器 Core 周期。** 完整 API 还包含 Keccak/SHAKE、采样、打包和清零。后续必须同时报告 Core、调用边界和完整 API 三层数据，才能得到有工程意义的端到端加速比。
3. **加速器搬运代价仍需独立测量。** 每组 148,160 / 101,760 B 是完整官方测试套件的 fixture 输入/输出量，不是 CPU 与加速器之间的通信量，也不在 API 计时窗口内。实际通信量取决于卸载边界、系数表示和片上复用；接入加速器后应实测搬运与同步，再评估 BRAM 常驻、批量命令和计算—搬运重叠。
4. **PYNQ-Z2 的第一版应保持参数 512。** 当前统一 64 KiB RAM、最大观测栈 12,928 B，固件有效镜像 26,272–27,808 B；这证明软件 baseline 可运行，但不代表 64 KiB 配置已经通过布局布线。资源与时序仍要用同一 Vivado 2024.2 工程实测。

## 当前分析的边界和下一次需要运行的实验

阶段 profiling 已由独立报告完成：[MLKEM512_PROFILE.md](MLKEM512_PROFILE.md)。该报告覆盖 Keccak-f、SHAKE/SHA3、采样、NTT、INTT、缓存式 BaseMul、mulcache、显式约减、编码和清零，并验证阶段独占周期逐例等于 API 区间。BRAM、LUT、FF、DSP、WNS 和 Fmax 仍需另行综合与实现测量。

阶段 profiling 已使用 RV32IM 快速乘法配置及同一组 ML-KEM-512 官方输入完成。API 外层保留前后两次 `rdcycle`，函数内部通过 MMIO 写入阶段进入/退出事件，由 RTL testbench 按嵌套栈累计 exclusive 周期；子阶段运行时不再累计父阶段，从而避免重复计数。

阶段结果包括 Keccak-f、SHAKE/SHA3、矩阵生成与 rejection sampling、噪声与 CBD、NTT、逆 NTT、缓存式 BaseMul 累加、mulcache、显式模约减、加减法、编码、清零和未归类 API 工作。

插桩固件的外层 API 周期包含事件写入和插桩造成的编译变化，已与历史无插桩基线分开报告，并核对阶段加总、嵌套平衡及官方输出。函数内联的 Montgomery/Barrett 运算仍归入 NTT、逆 NTT 或 BaseMul 等所属阶段；“显式模约减”不能解释为所有模运算的总成本。阶段数据经验证并给出结果链接后，才能据此判断主要瓶颈。

当前 profiling 不连接加速器，CPU→BRAM、BRAM→CPU、启动/等待和结果回收仍是后续集成实验。下一步先建立 [软件/硬件接口契约](MLKEM512_ACCELERATOR_INTERFACE.md) 和阶段 oracle，再测量这些成本并评估双缓冲、多 PE 或自定义命令队列。

## 结论

目前已经有一条可信的 CPU baseline：在相同 portable C、内存、输入和计时边界下，RV32IM 快速乘法将完整 512 API 算法区间周期降低约一半；逐条 M 指令关系验证了 CPU 执行差异，key-check 反例说明收益取决于具体运算组成。阶段 profiling 已证明 Keccak 是主要瓶颈，下一步转入接口契约、阶段 oracle 和标准库向量 BaseMul 接入，再用未插桩 API 测量真实软硬件收益。
